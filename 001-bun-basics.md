## ⚡ Introduction

### What Is Bun?

- Bun is a modern JavaScript runtime similar to Node.js — a tool used to run JavaScript code. It was created by **Jarred Sumner** as a replacement for Node.js
- Built using the **Zig** programming language
- Based on **WebKit's JavaScriptCore** (not V8, like Node.js)
- Free and open source

> Reference: [bun.sh](https://bun.sh/)

### Why Bun?

- **Faster** than Node.js
- Supports **JavaScript and TypeScript** out of the box — no extra setup needed
- **All-in-one tool**: runtime, test runner, and package manager are all built in

### The Toolchain at a Glance

Bun isn't just a faster Node.js — it replaces several separate tools with one binary. Knowing which piece does what explains most of what follows in this guide:

| Piece | Role |
| --- | --- |
| `bun` | The JavaScript/TypeScript runtime — executes files directly, no separate transpile step |
| `bun install` | The package manager — Node.js/NPM compatible, reads and writes `bun.lockb` |
| `bun test` | The built-in, Jest-compatible test runner |
| `bun build` | The bundler and standalone-executable compiler |
| `bunfig.toml` | Bun-specific configuration that doesn't belong in `package.json` |

> **Key Insight:** Every one of those pieces ships inside the single `bun` binary — there's no separate install for a test runner or a bundler. That's also why `bun.lockb` is a **binary** file instead of a JSON lockfile like `package-lock.json`: it's optimized for how fast Bun itself needs to read it, not for external tooling. See [Cache](#cache) and [Test Runner](#-test-runner) for how those pieces show up in practice.

## 🔷 TypeScript & JSX

Both are supported directly by the runtime — neither needs a separate compile step before `bun run` can execute it.

### TypeScript

Bun supports TypeScript natively by default. The `jsconfig.json` file (generated by `bun init`) can be renamed to `tsconfig.json` for TypeScript projects. TypeScript is also included as a default dev dependency in `package.json`.

> **Note:** Bun still doesn't *type-check* your code — it strips types the same way Babel does. Run `tsc --noEmit` separately if you want real type errors caught before they reach production.

### JSX / TSX

Bun also supports **JSX** and **TSX** (popularized by React). Install the required dependency first:

```bash
bun add react
bun add @types/react --dev
```

```tsx
const hello = <h1>Hello World!</h1>
console.info(hello)
```

## 🌿 Environment Variables

Bun automatically reads `.env` files — no external library required. Access variables using the `process` object:

```ts
console.log(process.env.DATABASE_HOST);
```

### NODE_ENV Support

If the `NODE_ENV` environment variable is set, Bun will automatically load the corresponding `.env.{NODE_ENV}` file.

| NODE_ENV value | File loaded |
| --- | --- |
| `production` | `.env.production` |
| `dev` | `.env.dev` |

> **Tip:** The plain `.env` file isn't replaced by this — it holds values that don't vary by environment, while `.env.{NODE_ENV}` layers the environment-specific overrides on top.

## 📦 Package Manager

Bun has a built-in package manager compatible with NPM. No additional installation required.

### Install Dependencies

```bash
bun install
```

> **Note:** Bun stores lock information in `bun.lockb` (a binary file) instead of `package-lock.json`, for faster reads.

To install **production dependencies only**:

```bash
bun install --production
```

### Manage Dependencies

| Action | Command |
| --- | --- |
| Add dependency | `bun add <name>` |
| Remove dependency | `bun remove <name>` |
| Update all dependencies | `bun update` |

### Cache

Downloaded packages are cached at `$USER/.bun/install/cache`. Packages with the same version are reused from cache, speeding up future installs.

## 🧪 Test Runner

Bun has a **built-in test runner** compatible with **Jest**. If you're familiar with Jest, your existing test code will work in Bun.

```bash
bun test
```

Run tests in watch mode:

```bash
bun test --watch
```

### Example

**`src/hello.ts`**

```ts
export function sayHello(name: string): string {
  return `Hello ${name}`;
}
```

**`test/hello.test.ts`**

```ts
import { describe, it, expect } from "bun:test"
import { sayHello } from "../src/hello"

describe('Bun Test Runner', () => {
  it('should support unit test', async () => {
    const response = sayHello('Dzaru')
    expect(response).toBe('Hello Dzaru')
  })

  it("should support unit test with budi", async () => {
    const response = sayHello("Budi");
    expect(response).toBe("Hello Budi");
  });
})
```

```text
bun test v1.3.12 (700fc117)

test/hello.test.ts:
✓ Bun Test Runner > should support unit test [0.34ms]
✓ Bun Test Runner > should support unit test with budi

 3 pass
 0 fail
```

## 🗂️ Workspace

Bun's package manager supports **workspaces** — a feature for managing multiple packages/sub-projects within a single repository.

### Setup

1. Create a `packages/` folder for sub-packages
2. Initialize each sub-package with `bun init`
3. Declare workspaces in the root `package.json`:

   ```json
   {
     "name": "study-bun",
     "workspaces": [
       "packages/*"
     ]
   }
   ```

4. Run `bun install` to symlink all sub-packages into `node_modules`

### Using Sub-packages

```ts
import { User } from "user/user.ts";

const user = new User("John Doe");
console.log(user.name); // John Doe
```

> **Note:** That import resolves through a **symlink** `bun install` created in step 4, not a copy — editing the sub-package's source is reflected immediately in every workspace that depends on it, with no rebuild step.

## 📚 Bun Standard Library

Bun provides its own standard library, accessible via the global `Bun` variable.

> ⚠️ **Warning:** Code that uses the `Bun` global **will not run in Node.js** — unlike the [Web API Support](#-web-api-support) above, which is portable across runtimes.

### HTTP Server

> Reference: [bun.sh/docs/api/http](https://bun.sh/docs/api/http)

```ts
Bun.serve({
  port: 3000,
  fetch: (request) => {
    const url = new URL(request.url);
    const name = url.searchParams.get("name") || "World";
    return new Response(`Hello ${name}`);
  },
});
```

| URL | Response |
| --- | --- |
| `http://localhost:3000` | `Hello World` |
| `http://localhost:3000/?name=Dzaru` | `Hello Dzaru` |

### File I/O

> Reference: [bun.sh/docs/api/file-io](https://bun.sh/docs/api/file-io)

```ts
const file = Bun.file(".env");
const content = await file.text();
console.log(content);

await Bun.write(".env.test", content);
```

### Hashing

> Reference: [bun.sh/docs/api/hashing](https://bun.sh/docs/api/hashing)

```ts
const password = "secret";

const hash = await Bun.password.hash(password, {
  algorithm: "bcrypt",
  cost: 10,
});

const result = await Bun.password.verify(password, hash, "bcrypt");
console.log(result); // true
```

### Semantic Versioning

> Reference: [bun.sh/docs/api/semver](https://bun.sh/docs/api/semver)

Bun includes a built-in library for semantic versioning checks.

### Utilities

> Reference: [bun.sh/docs/api/utils](https://bun.sh/docs/api/utils)

```ts
console.log(Bun.version);           // 1.3.12
console.log(Bun.revision);          // 700fc117...
console.log(Bun.env.DATABASE_HOST); // localhost
```

## 🌍 Bun Ecosystem

Bun is designed to be **compatible with the Node.js ecosystem** from the start, meaning most Node.js/NPM libraries work in Bun without changes.

| Library | Purpose | Install |
| --- | --- | --- |
| **Winston** | Logging | `bun add winston` |
| **ExpressJS** | HTTP server | `bun add express` |
| **Zod** | Validation | `bun add zod` |
| **Prisma ORM** | Database ORM | `bun add prisma --dev` |

### Winston (Logging)

```ts
import winston from "winston";

const logger = winston.createLogger({
  format: winston.format.json(),
  level: "debug",
  transports: [new winston.transports.Console()],
});

logger.info("Hello World");
logger.warn("Hello World");
logger.error("Hello World");
```

### ExpressJS

```ts
import express from "express";

const app = express();

app.get("/", (req, res) => {
  res.send("Hello World!");
});

app.listen(3000, () => {
  console.log("Server started on port 3000");
});
```

> **Note:** Bun ships its own [HTTP server](#http-server) via `Bun.serve` — reach for Express when you need its middleware ecosystem, not because Bun lacks a server API.

### Zod

```ts
import { z } from "zod";

const loginValidation = z.object({
  username: z.string().min(1).max(50).email(),
  password: z.string().min(1).max(50),
});

loginValidation.parse({
  username: "dzaru@example.com",
  password: "dzaru1234",
});
```

### Prisma ORM

Initialize and generate:

```bash
bun add prisma --dev
bunx prisma init --datasource-provider mysql
bunx prisma migrate dev
bunx prisma generate
```

**`prisma/schema.prisma`**

```prisma
model Contact {
  id    Int    @id @default(autoincrement())
  name  String @db.VarChar(100)
  phone String @db.VarChar(20)
  email String @db.VarChar(100)

  @@map("contacts")

```

```ts

const prisma = new PrismaClient();

const contact = await prisma.contact.create({
  data: {
    name: "Dzaru Rizky Fathan Fortuna",
```

## 🔨 Build

Bun can bundle and compile your project into a single output file.

```bash
bun build input.ts --outdir dist
```

| Flag | Description |
| --- | --- |
| `--outdir <folder>` | Output directory |
| `--minify` | Minify the output for a smaller file size |
| `--sourcemap` | Generate a source map for debugging |

```bash
bun build hello.ts --outdir dist --minify --sourcemap
```

```text
Bundled 2 modules in 24ms

  hello.js      152 bytes  (entry point)
  hello.js.map  466 bytes  (source map)
```

## 💾 Executable File

Bun can compile your project into a **standalone executable** — including all dependencies and the Bun runtime itself. No Bun installation is needed to run the output.

> **Gotcha:** Use `--outfile`, not `--outdir`, whenever `--compile` is set — a compiled executable is a single binary, not a directory of bundled modules.

```bash
bun build express.ts \
  --compile \
  --minify \
  --sourcemap \
  --outfile build/express \
  --target=bun-linux-arm64
```

Run on any machine (e.g. Docker):

```bash
docker run --rm -p 3000:3000 -v $(pwd)/build:/app ubuntu:22.04 /app/express
# Server started on port 3000

curl "http://localhost:3000?name=Dzaru"
# Hello Dzaru
```

| Concept | Purpose | Key Syntax |
| --- | --- | --- |
| **Runtime** | Run JS/TS directly, no build step | `bun run file.ts` |
| **Watch Mode** | Auto-reload on file change | `bun --watch run index.ts` |
| **Install** | Install dependencies | `bun install` |

| **Config** | Bun-specific settings | `bunfig.toml` |

| **Build** | Bundle for deployment | `bun build input.ts --outdir dist` |
| **Compile** | Standalone executable | `bun build input.ts --compile --outfile app` |

## 💡 Best Practices

**✅ Do This**

- **Use `bun init`** to scaffold projects, choosing a `.ts` entrypoint for TypeScript projects
- **Rename `jsconfig.json` to `tsconfig.json`** for full TypeScript editor support
- **Use `bunfig.toml`** for Bun-specific configuration (test root, coverage, log level) instead of overloading `package.json`
- **Use `bun install --production`** in production environments to skip dev dependencies
- **Run `bun update`** regularly to keep packages current
- **Use `--watch`** during development so the process restarts itself on file changes
- **Use `bunx`** instead of `npx` for running package executables
- **Use workspaces** for monorepo setups with multiple sub-packages
- **Enable `coverage = true`** in `bunfig.toml` to track test coverage
- **Always pair `--minify` with `--sourcemap`** when building for production, so a minified stack trace still maps back to source
- **Specify `--target`** when cross-compiling (e.g. `bun-linux-arm64` for Linux ARM)

**❌ Avoid This**

- **Assuming `bun.lockb` is human-diffable** — it's binary; review dependency changes by their `package.json` diff instead
- **Skipping `--outfile` when using `--compile`** — `--compile` always produces one binary, never a directory
- **Reaching for Express by default** — `Bun.serve` needs no extra dependency; only add Express when you need its middleware ecosystem
- **Assuming Bun Standard Library code (`Bun.serve`, `Bun.file`, …) is portable** — it will not run under Node.js
- **Letting the lockfile drift** — run `bun update` deliberately rather than letting installed versions silently diverge from `package.json`
